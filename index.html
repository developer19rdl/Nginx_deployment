1 Overview

The Mallik ERP infrastructure migrates from an unproxied XAMPP Apache + PHP bundle to a robust Nginx reverse proxy fronting a Node.js / compiled Windows executable (server.exe), backed by native MariaDB and Memurai Redis. The migration consolidates four independent concerns — web serving, API gateway, database, and cache — into cleanly separated Windows services with a single ingress port exposed to the LAN.

This guide documents every change required across the stack: code modifications, environment variable updates, Nginx configuration, PKG executable packaging, Windows service installation via NSSM, and end-to-end verification. It is written for on-premises Windows Server deployments and includes static-IP replacement rules, subpath deployment notes (/MallikEngineering/), troubleshooting playbooks, and security hardening recommendations.

1.1 Context & rationale

The original XAMPP-based deployment had three structural problems that made it unsuitable for production rollout. First, XAMPP bundles Apache, MySQL, PHP, and Perl into a single monolithic process tree — there is no clean way to restart just the database without bouncing Apache, no way to upgrade PHP without re-testing the entire bundle, and no isolation between web-server and database failures. Second, the Node.js API was bound to 0.0.0.0:8000 and exposed directly to the LAN, bypassing any TLS termination, rate limiting, or access logging at the network edge. Third, the database was tied to the XAMPP process lifecycle — when XAMPP crashed, the database crashed with it, and recovery required manual intervention.

The new architecture decouples these concerns. Nginx becomes the single network ingress on port 80, proxying API and WebSocket traffic to a backend bound strictly to the loopback interface. MariaDB and Memurai run as independent Windows services with their own restart policies, so a database crash no longer takes the web tier down. The Node.js backend is compiled into a standalone server.exe via pkg, eliminating the Node.js runtime dependency on the production server and reducing the attack surface.

Note: The compiled server.exe still reads a plaintext .env file placed alongside it on disk. Treat the .env file as a secret — restrict NTFS permissions to the service account only and exclude it from version control.

3 IP configuration

When deploying to any on-premises client server, replace <SERVER_LAN_IP> with the client's actual static IP address (for example, 192.168.1.15). Below is the breakdown of IPs to change versus IPs that must remain 127.0.0.1 / localhost. Getting this distinction wrong is the single most common deployment failure, so it is worth reading carefully.

The principle is simple: anything the client browser needs to talk to uses the LAN IP; anything one server-side component needs to talk to another server-side component on the same box uses 127.0.0.1. This keeps loopback traffic off the network and prevents the backend from being directly addressable by other machines.

3.1 Settings to update to client static IP

These are the four settings that change per deployment. They govern how the outside world addresses the server and how the backend advertises itself.

Table 3.1 — Settings that must change per client server
ComponentFile pathSettingValue to set
Nginx conf/nginx.conf server_name server_name 192.168.1.15 localhost;
Backend .env app/.env APP_URL APP_URL = http://192.168.1.15
Backend Socket app/app/sockets/index.js cors.origin origin: "http://192.168.1.15"
Database Host app/.env DB_HOST 192.168.1.18 (or 127.0.0.1 if DB is local)
Tip: If you deploy to multiple client sites, parameterise these values. Wrap the four settings in a deployment script that prompts for the server LAN IP and substitutes them with sed (or PowerShell (Get-Content …) -replace) before starting the services.

3.2 Settings that must remain 127.0.0.1 / localhost

These are the settings that must not change regardless of the client's network. They all describe traffic that stays entirely on the server host and therefore uses the loopback interface. Changing them to the LAN IP would expose internal services to the network and is a security regression.

Table 3.2 — Settings that must remain 127.0.0.1 / localhost

Nginx API Proxy conf/nginx.conf proxy_pass /api/ http://127.0.0.1:8000/api/ Nginx connects to local Node/EXE instance internally
Nginx Socket Proxy conf/nginx.conf proxy_pass /socket.io/ http://127.0.0.1:8000/socket.io/ Nginx proxies local WebSocket port internally
Redis Client app/app/config/redisCleinet.js socket.host 127.0.0.1 Memurai/Redis service listens on local port 6379
Frontend API URL MallikNewVersion/.env REACT_APP_API_URL /api/ Relative route — automatically uses client browser IP
Important: The frontend uses relative URLs (/api/) deliberately. The browser automatically resolves these against whatever IP it used to load the page, so the same static bundle works on every client server without rebuilds. Never hard-code an IP into the frontend build.

4 Backend changes (Node.js Express & PKG executable)

For deployment, the Node.js backend is compiled into a standalone Windows executable (server.exe) using pkg. The executable runs bound to 127.0.0.1:8000 and reads the .env file placed alongside it. This eliminates the Node.js runtime dependency on the production server and reduces the deployment footprint to a single self-contained binary.

The change set is small but each item is load-bearing. Skipping any one will cause subtle runtime failures that are hard to diagnose — for example, omitting trust proxy manifests as every client appearing to originate from 127.0.0.1 in audit logs, which can break rate-limiting and IP-based access control downstream.

Table 4.1 — Backend change specification

4.1 PKG compilation

The pkg tool bundles a Node.js application into a single executable that includes the Node.js runtime, your JavaScript code, and any assets declared in package.json's pkg.scripts / pkg.assets fields. The result is a server.exe that can be copied to a fresh Windows Server with no Node.js install required.

# 1. Install pkg globally
npm install -g pkg

# 2. Make sure app/package.json declares the entry point + binary name
#    "bin": "server.js",
#    "pkg": { "targets": ["node18-windows-x64"], "outputPath": "dist" }

# 3. Build the Windows x64 executable
cd C:\path\to\app
pkg . --targets node18-windows-x64 --output dist/server.exe

# 4. Ship dist/server.exe + .env together — they MUST live in the same folder
#    .env is read at process startup via dotenv
Note: pkg was archived by Vercel in 2023 but still works for Node 18 binaries. For greenfield projects consider @vercel/ncc + @yao-pkg/pkg (community fork with Node 20+ support).

4.2 trust proxy — why it matters

When Nginx proxies a request to the backend, the TCP source IP that Express sees is 127.0.0.1 — Nginx itself, not the original client. Without trust proxy enabled, every req.ip in your code will resolve to 127.0.0.1, breaking IP-based rate limiting, audit logging, and geo-blocking.

Setting app.set("trust proxy", 1) tells Express to trust the X-Forwarded-For header set by Nginx (exactly one hop upstream). The value 1 is the proxy hop count — increase it if you chain multiple proxies (e.g., Cloudflare → Nginx → backend would use 2).

// server.js — immediately after `const app = express();`
const app = express();
app.set("trust proxy", 1);  // trust single Nginx proxy hop

// Now req.ip will be the real client IP, not 127.0.0.1
app.use((req, res, next) => {
  console.log(`${req.ip} ${req.method} ${req.path}`);
  next();
});
Warning: Never set trust proxy to true (unconditional) when your backend is reachable from untrusted networks. An attacker could forge X-Forwarded-For headers and spoof their IP. Setting it to the integer 1 limits trust to exactly one proxy hop, which is correct for a single-Nginx topology.

4.3 Socket.io CORS

Socket.io's CORS configuration must list the exact origin that the browser uses to load the SPA. Because the SPA is now served from http://192.168.1.15/MallikEngineering/, the browser's Origin header for the WebSocket upgrade will be http://192.168.1.15. Configure it explicitly:

// app/app/sockets/index.js
const io = require("socket.io")(server, {
  cors: {
    origin: "http://192.168.1.15",  // ← MUST match the SPA origin exactly
    methods: ["GET", "POST"],
    credentials: true
  }
});

The previous origin: "*" configuration is no longer acceptable: it allowed any website to open a WebSocket to the backend, which is a CSRF vector on state-changing socket events. Locking it down to the exact SPA origin closes that hole.

5 Frontend changes (React JS)

The React frontend requires four small but interdependent changes. The guiding principle is to remove every hard-coded IP from the build and replace it with relative paths, so the same static bundle can be shipped to every client server without rebuilds. The only IP-specific value that remains is the URL the browser uses to reach the server, and that is supplied at runtime by the user typing the server's LAN IP into the address bar.

Table 5.1 — Frontend change specification

5.1 Environment variables

React's REACT_APP_* env vars are inlined at build time, not read at runtime. This means changing them requires a rebuild. The migration replaces hard-coded URLs with relative paths so the same bundle works on every client server without rebuilds.

# MallikNewVersion/.env
# Old — IP hard-coded into the build (requires rebuild per client):
# REACT_APP_API_URL=http://192.168.1.15:8001/api/
# REACT_APP_IMAGE_URL=http://192.168.1.15:8001/

# New — relative paths; browser resolves against its own origin:
REACT_APP_API_URL=/api/
REACT_APP_IMAGE_URL=/

When the browser loads http://192.168.1.15/MallikEngineering/ and the React code makes a request to /api/user, the browser resolves that to http://192.168.1.15/api/user — hitting Nginx, which proxies it to the backend on 127.0.0.1:8000. The same bundle deployed to http://10.0.0.5/MallikEngineering/ would transparently use http://10.0.0.5/api/user. No rebuild, no env file edit.

5.2 homepage & BrowserRouter basename

The homepage field in package.json tells the React build process what URL prefix the app will be served from. When set to /MallikEngineering/, the build output prefixes all asset URLs (/MallikEngineering/static/js/main.xyz.js, etc.) so they resolve correctly when served from a subpath rather than the document root.

For client-side routing to work, BrowserRouter must also be told its basename. Without basename, the router assumes it owns the entire URL path and will break on refresh of any route other than the index.

// MallikNewVersion/src/App.js
import { BrowserRouter } from "react-router-dom";

<BrowserRouter basename="/MallikEngineering">
  {/* routes */}
</BrowserRouter>
Warning: The basename value must not have a trailing slash. "/MallikEngineering" is correct; "/MallikEngineering/" will break nested routes. The homepage in package.json, by contrast, must have a trailing slash. This asymmetry is a frequent source of broken deep-links.
Tip: After changing homepage or basename, always run npm run build and clear the browser cache before testing. Service workers (if registered) may serve a stale bundle that masks the change.

6 Nginx configuration

Nginx is the single ingress point for the entire stack. All HTTP traffic from LAN clients enters on port 80, and Nginx routes each request either to a static file in the React build/ directory or to the backend server.exe on 127.0.0.1:8000. The configuration below is the production-grade template; copy it into C:\nginx\conf\nginx.conf and adjust the server_name and alias path for the client server.

Two variants are documented: §6.1 Standard for normal deployments, and §6.2 Executable for when the backend is shipped as a compiled server.exe. The only difference between them is whether the API and Socket.io proxy blocks include a comment explaining that they target the executable; the actual proxy directives are identical because Nginx does not care whether the upstream is node server.js or server.exe — both listen on the same loopback port.

6.1 Standard configuration — React served at /MallikEngineering/

Warning: Because package.json homepage is now "/MallikEngineering/", Nginx must use location /MallikEngineering/ with alias (NOT root) pointing directly to the build/ folder. A redirect from / to /MallikEngineering/ is also added so users don't need to type the full path. 
# Nginx Server Configuration — Serving React at /MallikEngineering/ subpath
server {
    listen 80;
    server_name _ 192.168.1.15 localhost; # Replace 192.168.1.15 with actual client server static IP

    client_max_body_size 500m;

    # ── 1. Redirect root / to /MallikEngineering/ automatically ──
    location = / {
        return 301 /MallikEngineering/;
    }

    # ── 2. React Frontend served at /MallikEngineering/ subpath ──
    # IMPORTANT: Use ^~ /MallikEngineering/ so React build assets take precedence
    location ^~ /MallikEngineering/ {
        alias "C:/Users/Administrator/source/repos/Honda/Other Projects/Nginx demo/Mllik/MallikNewVersion/build/";
        index index.html;
        try_files $uri $uri/ /MallikEngineering/index.html;
    }

    # ── 3. API → Backend Proxy ──
    location /api/ {
        proxy_pass http://127.0.0.1:8000/api/;

        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }

    # ── 4. Socket.io WebSocket Proxy ──
    location /socket.io/ {
        proxy_pass http://127.0.0.1:8000/socket.io/;

        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";

        proxy_read_timeout 300s;
        proxy_send_timeout 300s;
    }

    # ── 5. Uploaded Document Folders (Proxied to Node.js backend) ──
    location /contractReview/ {
        proxy_pass http://127.0.0.1:8000/contractReview/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }

    location /uploads/ {
        proxy_pass http://127.0.0.1:8000/uploads/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}

6.2 Configuration — Executable (.exe) backend + subpath

Note: When deploying the backend as a compiled server.exe binary (via pkg), the Nginx /api/ and /socket.io/ proxy blocks remain 100% IDENTICAL. Only the frontend location block changes to serve React from /MallikEngineering/ using alias. 6.3 Directive reference

Each Nginx directive in the configuration above has a specific purpose. Understanding them individually helps when debugging or extending the configuration (e.g., adding TLS, rate limiting, or gzip).

Table 6.1 — Nginx directive reference
DirectivePurposeWhy it matters here
listen 80 Bind Nginx to port 80 on all interfaces Single ingress port — only port 80 needs to be open in the firewall
server_name _ 192.168.1.15 localhost Match requests by Host header _ is a catch-all wildcard; explicit IPs ensure correct matching when accessed by LAN clients or localhost
client_max_body_size 500m Maximum HTTP request body size Allows file uploads up to 500 MB (contract reviews, document uploads); default Nginx value of 1 MB would reject them
location = / { return 301 /MallikEngineering/; } Exact-match redirect from root Users typing http://SERVER_IP/ are auto-redirected to the SPA — no need to remember the subpath
location ^~ /MallikEngineering/ Prefix match with priority over regex The ^~ modifier ensures React build assets (logos, images, JS) take precedence over any regex location blocks
alias "C:/.../build/" Map URL prefix to filesystem path Use alias (NOT root) when the location prefix does not exist in the filesystem path. root would append the prefix to the path and break asset URLs
try_files $uri $uri/ /MallikEngineering/index.html Fallback chain for SPA routing Client-side routes like /MallikEngineering/dashboard return index.html so React Router can take over
proxy_http_version 1.1 Use HTTP/1.1 to upstream Required for WebSocket upgrade (Connection: upgrade) and keep-alive connection pooling to the backend
proxy_set_header X-Real-IP $remote_addr Pass real client IP to backend Combined with trust proxy on the backend, lets req.ip resolve to the actual client instead of 127.0.0.1
proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for Append client IP to XFF chain Standard header for proxy chains; allows multi-hop IP tracing
proxy_set_header Upgrade $http_upgrade Pass WebSocket Upgrade header Required for Socket.io — without this the WS handshake fails with 400/426 errors
proxy_set_header Connection "upgrade" Force Connection header to "upgrade" Overrides default close behavior; required for WebSocket persistence
proxy_read_timeout 300s Timeout for reading upstream response 5-minute timeout allows long-running operations (large reports, batch jobs) without Nginx closing the connection prematurely
Important: The distinction between alias and root is the #1 source of Nginx misconfiguration. root /var/www/build/; with location /MallikEngineering/ would serve files from /var/www/build/MallikEngineering/ — wrong. alias /var/www/build/; serves from /var/www/build/ — correct. When in doubt, test with nginx -t and verify with curl -I http://localhost/MallikEngineering/.

7 Step-by-step deployment

Follow these sequential steps when setting up the Mallik ERP stack on a fresh on-premises Windows Server machine. Each step depends on the previous one — do not skip ahead. The whole procedure takes about 60–90 minutes on a clean Windows Server 2022 install with all prerequisites downloaded.

7.1 Install server prerequisites

Install Node.js, MariaDB, Memurai Redis, and Nginx. Node.js is only required on the build machine (for pkg); the production server can run without it once the server.exe is in place. MariaDB, Memurai, and Nginx are all installed as native Windows services.

  1. Node.js (LTS): Download & run the Node.js installer, or run winget install OpenJS.NodeJS.LTS. Verify with node -v.
  2. MariaDB Database: Install standalone MariaDB on port 3306 (or 3307). Set root password and import the database schema: 
    mysql -u root -p -P 3306 server_mallik < C:\path\to\database_dump.sql
  3. Memurai Redis Service: Install Memurai Developer (Redis Windows service) using winget install --id Memurai.MemuraiDeveloper -e. Verify service running on port 6379.
  4. Nginx Web Server: Download Nginx Windows binary (e.g., nginx-1.30.4.zip from nginx.org) and extract to C:\nginx\.
Tip: Use Chocolatey to script the prerequisite install: choco install nodejs-lts mariadb memurai nginx -y. This makes the deployment reproducible across servers.

7.2 Configure & package backend

Configure the backend environment, verify the source changes, then compile to server.exe via pkg. The executable and the .env file must live in the same directory — pkg embeds the JavaScript but the runtime still reads .env from disk at startup.

  1. Open app/.env and set: 
    APP_HOST = 127.0.0.1
APP_URL = http://<SERVER_LAN_IP>
APP_PORT = 8000
DB_HOST = 127.0.0.1   # or database server IP
  2. Verify app/server.js includes app.set("trust proxy", 1); right after const app = express();.
  3. Verify app/app/sockets/index.js sets origin: "http://<SERVER_LAN_IP>".
  4. Compile Backend to Windows Executable (.exe) via PKG: 
    npm install -g pkg
cd C:\path\to\app && pkg . --targets node18-windows-x64
# Generates server.exe in project directory
  5. Launch executable on server (ensure .env is in the same folder as server.exe): 
    .\server.exe

7.3 Build frontend production bundle

The frontend must be rebuilt after every code or env change. The build output is a static build/ directory containing index.html, hashed JS/CSS bundles, and assets. This directory is what Nginx serves via the alias directive.

  1. Open MallikNewVersion/.env and set relative paths: 
    REACT_APP_API_URL=/api/
REACT_APP_IMAGE_URL=/
  2. Open MallikNewVersion/package.json and set: "homepage": "/MallikEngineering/"
    Warning: This tells React to prefix all asset paths with /MallikEngineering/ in the build output — must match the Nginx location block exactly.
  3. Compile the production bundle: 
    cd C:\path\to\MallikNewVersion && npm run build

7.4 Configure & start Nginx

Copy the configuration from §6 into C:\nginx\conf\nginx.conf, adjust the server_name and alias path for the client server, then test and start Nginx.

  1. Edit C:\nginx\conf\nginx.conf with the following key settings:
    • Set server_name _ <SERVER_LAN_IP> localhost; (the _ is a wildcard catch-all)
    • Add root redirect: location = / { return 301 /MallikEngineering/; }
    • Use alias (NOT root) for the frontend location block: 
      location /MallikEngineering/ {
    alias "C:\path\to\MallikNewVersion\build\";
    try_files $uri $uri/ /MallikEngineering/index.html;
}
  2. Test Nginx configuration syntax: 
    C:\nginx\nginx.exe -t
  3. Start Nginx: 
    C:\nginx\nginx.exe         # first start
# OR
C:\nginx\nginx.exe -s reload   # if updating an existing instance

7.5 Configure Windows Firewall (allow port 80 inbound)

Execute the following command in Administrator PowerShell to allow LAN client connections on port 80. No other inbound ports need to be opened — the backend, database, and cache are all loopback-only.

New-NetFirewallRule -DisplayName "Allow Nginx HTTP Port 80" `
    -Direction Inbound -Protocol TCP -LocalPort 80 -Action Allow
Tip: To audit the rule later: Get-NetFirewallRule -DisplayName "Allow Nginx*". To remove it: Remove-NetFirewallRule -DisplayName "Allow Nginx HTTP Port 80".

7.6 Configure Windows Services for auto-start

Use NSSM (Non-Sucking Service Manager) to install Nginx and the backend executable as Windows Services. This ensures both restart automatically on system boot and survive crashes.

  1. Install NSSM: choco install nssm -y (or download from nssm.cc)
  2. Nginx as Windows Service: 
    nssm install Nginx "C:\nginx\nginx.exe"
nssm start Nginx
  3. Backend (server.exe) as Windows Service: 
    nssm install MallikBackend "C:\path\to\server.exe"
nssm start MallikBackend
Note: NSSM sets the service working directory to the executable's folder by default, which is why .env must sit next to server.exe. If you need a different working directory, set it explicitly with nssm set MallikBackend AppDirectory "C:\path\to\app" before starting the service.

7.7 End-to-end verification

Once all services are running, verify each layer of the stack independently before declaring victory. The order matters: test from the server first, then from a LAN client, then exercise a real user flow.

  1. Open browser on the server: 
    http://localhost/  →  auto-redirects to  →  http://localhost/MallikEngineering/  ✓
  2. Open browser on any LAN client PC: 
    http://<SERVER_LAN_IP>/MallikEngineering/   ✓
  3. Test API directly from browser or Postman: 
    http://<SERVER_LAN_IP>/api/user   ✓
  4. Perform login, test data grid loads, and verify WebSocket connection in browser DevTools → Network tab → filter WS.
Tip: If the WebSocket handshake fails, check the browser DevTools Console for the exact error. 400 Bad Request usually means the Socket.io CORS origin mismatch. 502 Bad Gateway means the backend service is down or not listening on 127.0.0.1:8000. See §9 Troubleshooting for the full diagnostic matrix.

8 Subpath deployment (/MallikEngineering/)

If the client requires serving the application under a subpath (e.g., http://<SERVER_IP>/MallikEngineering/) instead of the root http://<SERVER_IP>/, make the following specific configuration updates. Subpath hosting is useful when multiple applications share a single domain, or when the ERP must coexist with another web app on the same Nginx server.

The key challenge with subpath hosting is that every layer — React build, React Router, image URLs, and Nginx — must agree on the prefix. A mismatch in any one layer produces broken assets, 404s on deep links, or images that fail to load.

Subpath code & config modifications table

Table 8.1 — Subpath deployment modifications
#File pathSetting / DirectiveValue for subpath deployment
1 MallikNewVersion/package.json homepage "homepage": "/MallikEngineering/"
2 MallikNewVersion/src/App.js BrowserRouter basename <BrowserRouter basename="/MallikEngineering">
3 MallikNewVersion/.env REACT_APP_IMAGE_URL REACT_APP_IMAGE_URL=/MallikEngineering/
4 MallikNewVersion/ Rebuild Production Bundle npm run build
5 conf/nginx.conf Frontend Location Block location /MallikEngineering/ { alias "C:/.../build/"; try_files $uri $uri/ /MallikEngineering/index.html; }

Nginx configuration snippet for subpath hosting

# Nginx Config for Hosting under http://<SERVER_IP>/MallikEngineering/
server {
    listen 80;
    server_name 192.168.1.15 localhost;

    client_max_body_size 500m;

    # ── 1. React Frontend Subpath (/MallikEngineering/) ──
    location /MallikEngineering/ {
        # NOTE: Use 'alias' with trailing slash for subpath directory mapping
        alias "C:/Users/Administrator/source/repos/Honda/Other Projects/Nginx demo/Mllik/MallikNewVersion/build/";
        try_files $uri $uri/ /MallikEngineering/index.html;
    }

    # ── 2. (Optional) Redirect root http://localhost/ -> http://localhost/MallikEngineering/ ──
    location = / {
        return 301 /MallikEngineering/;
    }

    # ── 3. API Proxy ──
    location /api/ {
        proxy_pass http://127.0.0.1:8000/api/;
        proxy_http_version 1.1;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;
    }

    # ── 4. Socket.io Proxy ──
    location /socket.io/ {
        proxy_pass http://127.0.0.1:8000/socket.io/;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection "upgrade";
        proxy_read_timeout 300s;
    }
}
Warning: When changing from root deployment to subpath (or vice versa), every layer must be updated together. A common failure mode is updating homepage but forgetting basename — the app loads but deep links to /MallikEngineering/users return Nginx 404 because the router does not recognise the prefix.

9 Troubleshooting

This section catalogues the most common deployment failures, their symptoms, root causes, and fixes. When diagnosing, always start from the bottom of the stack (is the database running?) and work upward — most "the app is down" reports are actually a stuck Windows Service or a misconfigured .env.

9.1 Symptom → cause → fix matrix

Table 9.1 — Common deployment failures

502 intermittently, every ~60s Nginx keep-alive timeout > backend idle timeout Check Nginx error.log for "upstream prematurely closed" Add keepalive 32; in upstream block and proxy_next_upstream error timeout http_502;

10 Security hardening

The default deployment is functional but not production-hardened. This section lists additional security controls to apply before exposing the server to a wider network or to the internet. Treat each item as a checklist: not all are mandatory for every deployment, but each should be consciously accepted or rejected with a documented reason.

10.1 Network layer

  • Restrict port 80 to known LAN subnets. Replace the wildcard firewall rule with a scoped one: 
    New-NetFirewallRule -DisplayName "Allow Nginx HTTP Port 80 (LAN only)" `
    -Direction Inbound -Protocol TCP -LocalPort 80 -Action Allow `
    -RemoteAddress 192.168.1.0/24,192.168.2.0/24
  • Disable unnecessary inbound ports. Audit with Get-NetFirewallPortFilter | Where-Object { $_.LocalPort -lt 5000 } and remove any rule exposing 3306, 6379, or 8000 to the LAN.
  • Place the server behind a corporate firewall with egress filtering if internet access is not required for the application itself.

10.2 Transport layer (TLS)

HTTP on port 80 is acceptable for LAN-only deployments behind a corporate firewall, but TLS should be added for any deployment that handles authentication tokens, session cookies, or sensitive user data. Use Let's Encrypt (with win-acme for auto-renewal on Windows) or an internal CA for on-prem deployments.

# Nginx TLS snippet (add to server block, replace listen 80)
listen 443 ssl http2;
listen 80;
return 301 https://$host$request_uri;   # force HTTPS redirect

ssl_certificate     C:/nginx/ssl/mallik.crt;
ssl_certificate_key C:/nginx/ssl/mallik.key;
ssl_protocols       TLSv1.2 TLSv1.3;
ssl_ciphers         HIGH:!aNULL:!MD5;
ssl_session_cache   shared:SSL:10m;
ssl_session_timeout 10m;

# HSTS — only enable after confirming HTTPS works end-to-end
add_header Strict-Transport-Security "max-age=31536000; includeSubDomains" always;
Warning: Enabling HSTS is a one-way door — once a browser sees the header, it will refuse to connect via HTTP for the next max-age seconds. Test with max-age=300 first, then increase to a year once you are confident.

10.3 Application layer

  • Restrict .env file NTFS permissions to the service account only: 
    icacls C:\path\to\server.exe\.env /inheritance:r
icacls C:\path\to\server.exe\.env /grant:r "MallikBackendUser:(R)"
  • Rotate database credentials on a quarterly cadence. Use a dedicated MariaDB user with the minimum privileges required (no GRANT ALL). 
    CREATE USER 'mallik_app'@'127.0.0.1' IDENTIFIED BY 'strong-password';
GRANT SELECT, INSERT, UPDATE, DELETE ON server_mallik.* TO 'mallik_app'@'127.0.0.1';
FLUSH PRIVILEGES;
  • Set a strong Redis password in memurai.conf: 
    requirepass YourStrongRedisPasswordHere
bind 127.0.0.1
protected-mode yes
    Then update app/app/config/redisCleinet.js to authenticate.
  • Add security headers in Nginx: 
    add_header X-Content-Type-Options "nosniff" always;
add_header X-Frame-Options "SAMEORIGIN" always;
add_header Referrer-Policy "strict-origin-when-cross-origin" always;
add_header Content-Security-Policy "default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline';" always;

10.4 OS layer

  • Run services as a low-privilege account, not LocalSystem. Create a dedicated MallikBackendUser with Log on as a service right and use NSSM's nssm set MallikBackend ObjectName ".\MallikBackendUser" "password".
  • Enable Windows Defender with real-time protection and add folder exclusions only for the Nginx log directory and MariaDB data directory (not for the executable).
  • Enable automatic Windows Updates with active hours configured to the maintenance window.
  • Restrict RDP access to a single admin jump host; never expose RDP (port 3389) to the internet.

11 Performance tuning

Once the stack is stable, tune for throughput and latency. The defaults in the configuration above are conservative; the values below are starting points for production load. Always benchmark before and after each change using a tool like ab or k6.

11.1 Nginx tuning

# nginx.conf — top-level (outside server block)
worker_processes auto;        # one worker per CPU core
worker_rlimit_nofile 65535;   # raise FD limit

events {
    worker_connections 4096;  # concurrent connections per worker
    use epoll;                # Linux only; on Windows leave default
    multi_accept on;
}

http {
    # ── Connection pooling to upstream ──
    upstream backend {
        server 127.0.0.1:8000;
        keepalive 32;             # maintain 32 idle conns to backend
    }

    # ── Gzip compression ──
    gzip on;
    gzip_vary on;
    gzip_min_length 1024;
    gzip_types text/plain text/css application/json application/javascript text/xml application/xml text/javascript image/svg+xml;

    # ── Static asset caching ──
    location ~* \.(js|css|png|jpg|jpeg|gif|ico|svg|woff2?)$ {
        expires 1y;
        add_header Cache-Control "public, immutable";
        access_log off;
    }

    # ── Use the upstream pool in proxy blocks ──
    location /api/ {
        proxy_pass http://backend/api/;
        proxy_http_version 1.1;
        proxy_set_header Connection "";   # enable keepalive
        # … rest of proxy headers …
    }
}

11.2 Backend (Node.js / server.exe) tuning

  • Cluster mode: If running node server.js directly, use PM2 cluster mode to fork one process per core. For server.exe, run multiple instances on different ports (8001, 8002, …) and load-balance via Nginx upstream.
  • UV_THREADPOOL_SIZE: Default is 4. Raise to 16–32 for I/O-heavy workloads (file uploads, DB queries). 
    # Set in .env or as environment variable before launching server.exe
UV_THREADPOOL_SIZE=16
  • Node max old space size: Raise the V8 heap limit for memory-heavy operations. 
    # For node directly:
node --max-old-space-size=4096 server.js

# For pkg exe — set NODE_OPTIONS env var before launch:
set NODE_OPTIONS=--max-old-space-size=4096
server.exe

11.3 MariaDB tuning

Edit my.ini (typically in C:\Program Files\MariaDB XX.X\data\) and restart the service. Values below are for a server with 16 GB RAM; scale proportionally.

# my.ini — key buffer / pool settings
[mysqld]
innodb_buffer_pool_size = 4G        # ~25-50% of total RAM
innodb_log_file_size    = 512M
innodb_flush_log_at_trx_commit = 2  # 1=ACID, 2=perf (1s data loss on crash)
innodb_flush_method     = O_DIRECT
max_connections         = 200
query_cache_type        = 0         # query cache is deprecated in MySQL 8; leave off
tmp_table_size          = 64M
max_heap_table_size     = 64M

11.4 Memurai / Redis tuning

# memurai.conf
maxmemory 512mb                 # cap memory usage
maxmemory-policy allkeys-lru    # evict least-recently-used keys
timeout 300                    # close idle clients after 5 min
tcp-keepalive 60               # TCP keepalive interval
save ""                        # disable RDB persistence if cache-only
Tip: Always benchmark before and after tuning. A 5-minute load test with k6 against your realistic API mix will surface bottlenecks far more reliably than guessing. Common surprises: the bottleneck is the database (not Nginx), or file I/O on uploads (not CPU).

12 FAQ

Short answers to the questions that come up most often during deployment. If your question is not here, search the article using the search box at the top, or check §9 Troubleshooting.

Q: Can I keep using XAMPP's MySQL instead of installing native MariaDB?

Technically yes — XAMPP's MySQL is just MariaDB under the hood. But you lose the primary benefit of decoupling: XAMPP's MySQL dies when XAMPP crashes. Installing native MariaDB as a Windows Service gives you independent restart, independent upgrade path, and independent backup. The migration is a 30-minute mysqldump + mysql < dump.sql cycle.

Q: Do I need Node.js installed on the production server?

No. The pkg compilation bundles the Node.js runtime into server.exe. The production server only needs server.exe + .env + MariaDB + Memurai + Nginx. Node.js is only required on the build machine.

Q: Why use alias instead of root in Nginx?

root appends the URL path to the filesystem path. With location /MallikEngineering/ { root C:/build/; }, Nginx looks for files at C:/build/MallikEngineering/index.html — wrong. With alias, Nginx strips the location prefix and serves from C:/build/index.html — correct. Use alias whenever the URL prefix does not exist in the filesystem.

Q: The frontend shows a blank white page. What's wrong?

Open browser DevTools → Console. The most common causes are: (1) homepage in package.json does not match the Nginx location prefix — assets 404; (2) BrowserRouter basename has a trailing slash; (3) mixed content — page loaded over HTTPS but assets requested over HTTP. Fix the mismatches, rebuild, redeploy.

Q: Can I run multiple Mallik ERP instances on one server?

Yes. Run multiple backend executables on different loopback ports (8001, 8002), and add multiple server blocks in Nginx (one per domain or subpath). Each instance needs its own database schema and .env. Use separate Windows Service names (MallikBackend-ClientA, MallikBackend-ClientB).

Q: How do I rotate the .env secrets without downtime?

Update .env, then nssm restart MallikBackend. The restart takes 1–3 seconds; during that window Nginx returns 502 on API calls. For zero-downtime rotation, run two backend instances on different ports, drain one, restart it, then drain the other. This is overkill for most on-prem deployments.

Q: Should I add TLS (HTTPS)?

For LAN-only deployments behind a corporate firewall, HTTP is often acceptable. For any deployment that handles authentication tokens, session cookies, or PII, add TLS. See §10.2 for the Nginx TLS snippet and certificate options (Let's Encrypt via win-acme, or internal CA).

Q: pkg is archived — should I still use it?

For Node 18 binaries already in production, pkg continues to work fine — it just receives no new features. For greenfield projects, consider @vercel/ncc (bundles to a single JS file, requires Node on target) or @yao-pkg/pkg (community fork with Node 20+ support). For a true single-binary deployment on Node 20+, consider Bun's --compile or Deno's compile.

Q: How do I back up the database?

Use mysqldump on a schedule via Windows Task Scheduler:

mysqldump -u root -p<password> --single-transaction --routines --triggers server_mallik > C:\backups\mallik_%date:~10,4%%date:~4,2%%date:~7,2%.sql

For point-in-time recovery, enable MariaDB binary logs and ship them to a backup target. Retain at least 7 days of daily dumps plus 4 weeks of weekly dumps.

Q: The frontend was built with the wrong homepage — do I need to rebuild?

Yes. homepage is a build-time setting; React inlines it into the asset URLs in index.html. There is no way to change it post-build without editing every <script src> and <link href> in index.html, which is fragile. Always rebuild after changing homepage.
